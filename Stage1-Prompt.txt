==================================================
DATA QUALITY / ANALYSIS LOGIC
==================================================

Implement practical, understandable rules for the MVP.

A. Statistical audit per column:
- inferred data type
- null count and null percentage
- uniqueness ratio
- duplicate frequency
- min / max / mean / median for numeric columns where applicable
- standard deviation where applicable
- outlier detection using a simple robust method
- invalid date parsing count for date-like columns
- inconsistent categorical formatting detection
- high-cardinality field detection
- suspicious identifier patterns

B. Reliability score (0-100):
Design a transparent scoring framework.
Example idea:
- start at 100
- subtract points for nulls
- subtract for duplicates
- subtract for inconsistent formats
- subtract for high anomaly rate
- subtract more heavily for critical insurance field failures
- map result to:
  - Green
  - Amber
  - Red

Make the scoring modular, configurable, and easy to tune.

C. Cross-dataset resolution:
- identify joinable fields such as policy_number, customer_id, quote_id, claim_id
- allow matching across datasets
- if one dataset has a null and another dataset has a trusted value for the same key, propose that fill
- log source dataset and key used

D. Sequence / interpolation engine:
For MVP, keep this conservative and rules-based.
Only propose interpolation when confidence is high and explainable.
Examples:
- missing sequential identifier between two valid neighbouring identifiers
- date or time sequence gaps where inference is straightforward
- simple forward/backward fill only when appropriate and clearly justified
Do NOT hallucinate values.
Every inferred value must include a reason and confidence score.

E. Insurance-specific guardrails:
Implement configurable critical fields such as:
- policy_number
- premium
- ncd
- inception_date
- expiry_date
- postcode
- product_type

If these are null or malformed, flag them heavily in scoring and report them clearly.

F. Entity mismatch detection:
- where unique identifiers align but supporting fields differ unexpectedly
- example: same policy_number but inconsistent postcode, name, product type, or premium across datasets
- flag as possible entity mismatch

G. Ghost join detection:
- detect likely join errors where datasets appear to join on a key but surrounding attributes strongly suggest mismatch
- surface these as warnings, not auto-fixes
